# 系统日志方案

> 2026-05-18 | 两表设计：按频率和保留策略分离

---

## 一、表结构

### 表 1：`support_sync_logs` — 数据同步日志

**频率：高（每天几十～几百条）。保留 30 天自动清理。**

记录所有从外部拉数据进来的操作（webhook / 兜底 / API 补全）。

```sql
CREATE TABLE IF NOT EXISTS support_sync_logs (
  id BIGSERIAL PRIMARY KEY,
  source       TEXT NOT NULL,          -- 'webhook' | 'backfill' | 'api'
  action       TEXT NOT NULL,          -- 'order_upsert' | 'order_list_page' | 'transaction_lookup' | 'backfill_summary'
  store_subdomain TEXT NOT NULL,
  target_id    TEXT,                   -- 订单号 / webhook topic
  items_total  INTEGER DEFAULT 0,     -- 本次处理多少条
  items_new    INTEGER DEFAULT 0,     -- 新增条数
  items_updated INTEGER DEFAULT 0,    -- 更新条数
  items_skipped INTEGER DEFAULT 0,    -- 跳过条数（已存在/无变化）
  status       TEXT NOT NULL DEFAULT 'success',  -- 'success' | 'partial' | 'failed'
  error_message TEXT,
  duration_ms  INTEGER,               -- 耗时毫秒
  detail_json  JSONB DEFAULT '{}'::jsonb,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_sync_logs_source ON support_sync_logs(source, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_sync_logs_store ON support_sync_logs(store_subdomain, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_sync_logs_status ON support_sync_logs(status, created_at DESC);
```

---

### 表 2：`support_operation_logs` — 操作日志

**频率：低（每天几十条）。永久保留。**

记录所有对数据库的写入操作。多步骤操作记录为一条，`detail_json` 中逐步骤标注成败。

```sql
CREATE TABLE IF NOT EXISTS support_operation_logs (
  id BIGSERIAL PRIMARY KEY,
  category     TEXT NOT NULL,          -- 'email' | 'ticket' | 'store' | 'webhook' | 'config' | 'backfill'
  action       TEXT NOT NULL,          -- 具体操作（见下方清单）
  actor        TEXT NOT NULL,          -- 'system' | agent_name | 'customer'
  actor_ip     TEXT,                   -- 管理员操作时记录 IP
  store_subdomain TEXT,
  target       TEXT,                   -- 操作对象：邮件任务号 / 工单号 / 店铺域名
  summary      TEXT NOT NULL,          -- 一行中文摘要
  status       TEXT NOT NULL,          -- 'success' | 'partial' | 'failed'
  failed_at_step TEXT,                 -- partial/failed 时，断在哪一步（步骤名）
  detail_json  JSONB DEFAULT '{}'::jsonb,  -- 各子步骤明细
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_op_logs_category ON support_operation_logs(category, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_op_logs_status ON support_operation_logs(status, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_op_logs_store ON support_operation_logs(store_subdomain, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_op_logs_target ON support_operation_logs(target);
```

## 二、`status` 三态定义

| status | 含义 | 触发条件 |
|--------|------|----------|
| `success` | 全部步骤成功 | 多步骤操作每一步都完成 |
| `partial` | ⚠️ 部分成功 | 至少一步成功、至少一步失败（如店铺创建成功但 webhook 注册失败） |
| `failed` | 全部失败 | 第一步就失败，后续未执行 |

`detail_json` 示例（partial — 店铺创建成功，webhook 注册失败，backfill 初始化照常执行）：

```json
{
  "steps": [
    { "step": "create_store_in_db",    "status": "success", "detail": "店铺 jaymiartstore 已创建" },
    { "step": "register_webhook",      "status": "failed",  "detail": "HTTP 401: Invalid access token" },
    { "step": "init_backfill_state",   "status": "success", "detail": "backfill_state 已初始化，首次同步时间=空" }
  ]
}
```

> **原则：子步骤之间不互相阻塞，除非强依赖（如第一步写 DB 失败则后续无意义）。**
> 每条 step 独立标注自己的 status，`failed_at_step` 只标第一个失败步骤用于排查，不影响后续步骤执行。

## 三、记录时机清单

### 3.1 店铺类 (category=`store`)

| action | 触发 | actor | 步骤 | 备注 |
|--------|------|-------|------|------|
| `store_create` | 管理员新增店铺 | agent | ① 写 DB → ② 注册 webhook → ③ 初始化 backfill_state | 三步任一失败即 partial/failed |
| `store_delete` | 管理员删除店铺 | agent | ① 注销 webhook → ② 删 DB 记录 | 注销失败仍删 DB = partial |
| `store_update` | 管理员修改 | agent | ① 更新 DB | 单步，直接成功/失败 |

### 3.2 Webhook 类 (category=`webhook`)

| action | 触发 | actor | 步骤 | 备注 |
|--------|------|-------|------|------|
| `webhook_register` | 管理员注册 | agent | ① 调 Shoplazza API → ② 更新 DB webhook_status | |
| `webhook_unregister` | 管理员注销 | agent | ① 调 Shoplazza API → ② 更新 DB | |

### 3.3 邮件类 (category=`email`)

| action | 触发 | actor | 步骤 |
|--------|------|-------|------|
| `job_created` | webhook/兜底/手动 | system/agent | ① 检查幂等 → ② 写 email_jobs |
| `job_sent` | worker 发送成功 | system | ① 调 SMTP → ② 更新 job 状态为 sent |
| `job_failed` | worker 发送失败 | system | ① 调 SMTP → ② 更新 job 状态为 failed + 记录错误 |
| `job_resent` | 管理员补发 | agent | ① 生成新 token → ② 写新 job → ③ 立即发送 |
| `job_cancelled` | 管理员取消 | agent | ① 更新 status=cancelled |

### 3.4 工单类 (category=`ticket`)

| action | 触发 | actor | 步骤 |
|--------|------|-------|------|
| `ticket_created` | 顾客提交 | customer | ① 写 tickets → ② 写首条 message |
| `agent_reply` | 管理员回复 | agent | ① 写 message → ② 更新 ticket updated_at → ③ (可选)创建通知邮件 |
| `customer_reply` | 顾客回复 | customer | ① 写 message → ② 更新 ticket |
| `ticket_status_changed` | 管理员改状态 | agent | ① 更新 status → ② 若关闭则设 closed_at |
| `ticket_closed` | 工单关闭 | agent/customer | ① 更新 → ② (可选)发关闭通知 |

### 3.5 配置类 (category=`config`)

| action | 触发 | actor | 步骤 |
|--------|------|-------|------|
| `auto_send_toggled` | 管理员切换 | agent | ① 更新 email_settings |
| `auto_backfill_toggled` | 管理员切换 | agent | ① 更新 email_settings |

### 3.6 兜底类 (category=`backfill`)

| action | 触发 | actor | 步骤 |
|--------|------|-------|------|
| `backfill_manual_trigger` | 手动触发 | agent | ① 记录触发 |
| `backfill_auto_run` | 每小时自动 | system | ① 检查开关 → ② 逐店铺执行 |
| `backfill_store_complete` | 单店兜底完成 | system | ① 记录该店 sync 汇总 |

> 兜底的逐页拉取详情记在 `support_sync_logs`，不重复记到 `operation_logs`。

## 四、sync_logs 记录时机

| source | action | 触发 | items_total | items_new | items_updated | 说明 |
|--------|--------|------|:--:|:--:|:--:|------|
| `webhook` | `order_upsert` | webhook 收到 orders/paid | 1 | 0/1 | 0/1 | 看快照是否新建 |
| `api` | `order_upsert` | API 单独补全 | 1 | 0/1 | 0/1 | |
| `backfill` | `backfill_summary` | 兜底单店完成 | N | N_new | N_upd | 每店一条汇总 |
| `backfill` | `transaction_lookup` | 查卡号 | 1 | - | - | 是否拿到 card_last4 |
| `backfill` | `order_list_page` | 单页拉取 | 10 | - | - | has_more=true/false |

## 五、清理策略

```typescript
// index.ts 启动时 + 每 24h 执行一次
const retentionDays = Number(process.env.SUPPORT_SYNC_LOG_RETENTION_DAYS) || 30;
await query(`DELETE FROM support_sync_logs WHERE created_at < now() - interval '${retentionDays} days'`);
```

| 表 | 保留 | 清理 |
|------|------|------|
| `support_sync_logs` | 30 天（可配置） | 定时 DELETE |
| `support_operation_logs` | **永久** | 不自动清理 |
