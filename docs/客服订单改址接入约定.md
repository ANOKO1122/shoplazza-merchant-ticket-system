# 客服订单收货地址修改：两套系统接入约定 v1

本系统客服页面和 Maildesk 使用同一条改址队列：提交请求 → 实时读取店匠并检查冲突 → 修改店匠 → 再次读取确认 → 同步本地地址。只有状态为 `succeeded` 才可向客服显示“已同步到店匠”。

马帮接收店匠地址变更已由业务方确认，本项目负责店匠与本地订单地址。此次不改变客服回复、邮件任务、付款状态、工单状态和物流记录。

## 1. 数据库连接与权限

- 现有 `order_reader` 连接保留，继续只读。
- 新账号为 `order_address_writer`。连接密码通过单独的私有文件交付，不写入 Git。
- 数据库：`support_portal`；端口：`5432`；使用 TLS。连接地址、密码、CA 证书及可复制 URI 见私有交付文件。
- 沿用现有 Maildesk 服务出口 IP `114.55.166.61`。其他出口地址需要另行配置访问规则。
- 新账号可读取 `support_order_snapshots`、`support_shipping_address_requests`，并执行六参数函数 `support_submit_shipping_address_change`。
- 写入范围限于提交地址修改请求。订单快照、请求状态、日志、店铺令牌等不授予直接写权限。
- 建议连接池不超过 4；账号连接数上限 8；单条 SQL 和空闲事务超时均为 15 秒。

**不要直接 UPDATE `support_order_snapshots.shipping_address_json` 或 `raw_order_json`。** 直接改快照不会调用店匠，也不能完成改址。不要修改或绕过请求状态。

## 2. 订单身份与编辑原值

订单唯一业务身份是 `store_subdomain + order_id`，其中 `order_id` 是数据库保存的店匠订单 ID，不能用展示用的 `order_number` 代替。相同订单可能有多个顾客邮箱快照；邮箱不作为改址目标。

编辑前读取原始 JSON，并保留完整对象直到提交：

```sql
SELECT store_subdomain, order_id, order_number, shipping_address_json
FROM public.support_order_snapshots
WHERE store_subdomain = $1 AND order_id = $2
ORDER BY updated_at DESC, id DESC
LIMIT 1;
```

`shipping_address_json` 是本地快照，可能落后于店匠。后端执行时会与实时店匠地址比对；不一致就返回 `conflict`，不会覆盖最新地址。此时用请求结果中的 `after_address_json` 展示店匠当前地址，客服核对后以它作为新的编辑原值。

打开订单时同时检查正在进行的改址，便于页面刷新后恢复，也避免两套客服重复操作：

```sql
SELECT id::text, source, actor, status, error_code, error_message,
       before_address_json, desired_address_json, after_address_json,
       created_at, updated_at
FROM public.support_shipping_address_requests
WHERE store_subdomain = $1 AND order_id = $2
  AND status IN ('pending', 'processing', 'uncertain')
ORDER BY id DESC
LIMIT 1;
```

## 3. 提交修改：只调用这个函数

```sql
SELECT public.support_submit_shipping_address_change(
  $1::text,   -- store_subdomain，使用数据库原值
  $2::text,   -- order_id，使用数据库原值
  $3::jsonb,  -- patch：只包含本次改变的字段
  $4::jsonb,  -- expected：客服开始编辑时的完整原地址
  $5::text,   -- actor：例如 maildesk:agent-123:张三
  $6::text   -- idempotency_key：本次编辑唯一 UUID
)::text AS request_id;
```

例如 patch（不要把示例当作真实订单执行）：

```json
{
  "first_name": "Jane",
  "address": "123 Example Street",
  "address1": "Apartment 4",
  "city": "Boston",
  "province": "Massachusetts",
  "province_code": "MA",
  "country": "United States",
  "country_code": "US",
  "zip": "02108"
}
```

执行后立即提交数据库事务。推荐使用自动提交。**不要持有事务等待店匠处理**，未提交的请求对后台 worker 不可见。

约定：

- 使用参数化 SQL，JSON 参数序列化传入，不拼接 SQL。
- `actor` 必填，包含对方系统的真实客服标识；数据库另记 `submitted_by`。该账号代表受信任的 Maildesk 后端，不应直接给浏览器使用。
- `source` 由函数固定为 `maildesk`，对方无需传入。
- 相同操作重试必须保留相同 UUID、原地址、patch 和 actor。同一幂等键与相同输入返回原请求 ID；同键不同输入会被拒绝。
- 网络中断时先用相同参数重试提交，或按 `source='maildesk' AND idempotency_key=$1` 查询，不能换 UUID 再提交。
- `id` 是 PostgreSQL BIGINT，客户端按字符串处理。
- 每个订单最多一个 `pending / processing / uncertain` 请求。已有请求时先读取其结果，不能并行覆盖。

## 4. 可修改字段

| 字段 | 含义 |
|---|---|
| `first_name`, `last_name` | 收件人名、姓，至少填写一项 |
| `phone`, `phone_area_code` | 电话、电话区号 |
| `country`, `country_code` | 国家名称、两位 ISO 国家代码，例如 US |
| `province`, `province_code` | 省州名称及代码 |
| `area`, `city` | 地区、城市 |
| `address` | 地址第一行 |
| `address1` | 地址第二行，例如楼栋、房间号 |
| `company`, `zip` | 公司、邮编 |

所有 patch 值必须为字符串；省略表示保持原值，`""` 表示清空该可选字段。不接受 `null`、未知字段或空 patch。单字段最多 1000 字符，patch 最大 16 KiB；原地址应为 JSON 对象。

特别注意：店匠这里的第一行是 **`address`**、第二行是 **`address1`**，没有 `address2`。修改国家/省州时应同时核对名称与代码，不能仅改名称保留旧代码。

不允许修改 `email`。后端会保留店匠原收货邮箱，不改变顾客账户邮箱、账单地址、价格、运费或物流单号。姓名、第一行地址、城市、国家必须有效。包含税号/证件等特殊地址字段的订单暂时要求在店匠后台修改，避免旧版 API 丢失特殊信息。

## 5. 查询结果与页面提示

```sql
SELECT id::text, status, error_code, error_message,
       before_address_json, desired_address_json, after_address_json,
       attempts, created_at, updated_at, completed_at
FROM public.support_shipping_address_requests
WHERE id = $1::bigint AND store_subdomain = $2 AND order_id = $3;
```

建议每 3 秒查询一次，离开页面停止轮询，重新打开时查询进行中的请求。后台每 3 秒检查新请求；请求会串行执行，实际耗时取决于队列和店匠响应，不能把“入队成功”显示成“改址成功”。

| 状态 | 对方应如何处理 |
|---|---|
| `pending` | 已入队，等待处理 |
| `processing` | 正在向店匠查询/保存/核对，继续查询 |
| `succeeded` | 店匠读回确认且本地事务已提交，可以显示成功；展示 `after_address_json` |
| `failed` | 本次未完成；展示错误。修复权限或输入后重新读取地址，以新 UUID 发起新操作 |
| `conflict` | 开始编辑后地址已有变化；展示 `after_address_json`，请客服重新核对，不自动覆盖 |
| `uncertain` | 请求可能已经到达店匠，但结果不能确认。展示“结果待确认”；禁止自动重写或换 UUID 重试 |

`uncertain` 后台约每 5 分钟只读核验，确认目标地址后可转为成功；不会自动再次 PUT。如果持续不一致，保留请求并由管理员核对店匠及请求记录处理，不能直接改状态来绕过保护。

常见 SQL 错误：`invalid_address_field / invalid_address_payload / invalid_request_identity` 为参数问题；`idempotency_key_reused` 为同一键换了输入；`active_address_request_exists` 为已有未完成请求；`store_unavailable / order_not_found` 为店铺或订单不可用。后端处理错误还可能包括缺少 `write_order`、已发货、地址已变化等，请展示 `error_message`。

## 6. 业务与一致性约定

- 第一版只允许未发货且未取消/完成的订单；执行前实时检查，部分发货也不可修改。
- 每次执行重新查询店匠写权限。用户后续补开权限即可生效；之前因权限失败的请求需要重新提交。
- 本系统保存成功后按店铺和订单更新全部邮箱快照中的两份收货地址，其余订单数据保留。
- 后台同步会保护已确认的新地址，旧数据不能覆盖；后续店匠合法新地址仍可进入本地。
- 两套客服共用同订单单个活动请求，且执行前比较地址原值。店匠 API 未提供已确认的原子条件更新接口，外部店匠后台在 GET 与 PUT 之间的并发编辑无法被本地锁完全排除。
- 本功能不调用本系统邮件发送流程。店匠 2025-06 文档未明确仅改地址是否触发其自身通知，不擅自设置订单通知开关。
- 请求表保存来源、客服、前后地址、时间与结果；系统操作日志也记录请求编号，便于定位。

## 7. 运维与验收

部署会由 `ensureTables()` 创建队列、地址保护状态和 SQL 函数。随后使用 `support-system/scripts/provision-address-writer.js` 创建专用账号；密码文件权限为 `0600`。PG 访问规则必须允许该账号从 Maildesk 出口 IP 通过 TLS 连接，保留旧 `order_reader` 规则。

交付给 Maildesk 的内容：本约定、私有连接文件、PG CA 证书。把 CA 放到目标系统并调整 URI 的 `sslrootcert` 路径，或在驱动中配置同一 CA 和证书校验。

对接验收应使用测试订单，检查：成功回读一致、原邮箱保留、权限不足、已发货拒绝、旧地址冲突、同 UUID 重试仅一条请求、超时不重复写入，以及本地付款/物流/邮件数据保持正常。本项目自动化测试使用隔离数据库和模拟店匠；不会为验收擅自修改真实顾客订单。

API 依据：[店匠 2025-06 更新订单](https://www.shoplazza.dev/api/202506/order-update)、[订单权限说明](https://www.shoplazza.dev/docs/app/building-blocks/authentication/access-scopes)。
