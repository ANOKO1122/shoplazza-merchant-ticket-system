# 手动发起新工单邀请 — 实施方案

## 需求概述

客服在工单详情页可手动给同一订单发起新的工单邀请。旧工单继续保留，同一订单允许存在多个工单。顾客走完整的 bootstrap 流程（邮件 → 链接 → 填写 → 提交 → 获得 ta_ token）。

## 1. 数据库改动

### 1.1 `support_tickets` — 移除唯一约束

```sql
-- 删除旧的唯一约束（注意：PostgreSQL 自动生成的约束名可能被截断，
-- 实际名称以 \d support_tickets 查到的为准，通常为 support_tickets_store_subdomain_order_id_customer_em_key）
ALTER TABLE support_tickets DROP CONSTRAINT IF EXISTS support_tickets_store_subdomain_order_id_customer_em_key;
```

> **重要**：`ensureTables()` 中仅修改 `CREATE TABLE IF NOT EXISTS` 的建表语句**不会**影响已存在的表。必须通过 `ALTER TABLE` 显式删除约束。在 `ensureTables()` 函数末尾增加此 ALTER 调用。
>
> 建表语句中去掉 `UNIQUE(store_subdomain, order_id, customer_email)` 仅对未来全新部署的数据库生效。

### 1.2 `support_access_tokens` — 增加 `force_new_ticket` 字段

```sql
ALTER TABLE support_access_tokens ADD COLUMN IF NOT EXISTS force_new_ticket BOOLEAN NOT NULL DEFAULT false;
```

> 建表语句中也同步增加 `force_new_ticket BOOLEAN NOT NULL DEFAULT false`。

> 用途：手动邀请生成的 bootstrap token 标记此字段为 `true`，bootstrap 端点据此跳过"已有工单"检测，始终返回 `mode: 'new_ticket'`。

### 1.3 `support_email_templates` — 插入新类型默认模板

## 2. Token 层改动 (`src/token.ts`)

### 2.1 `storeToken` — 增加 `forceNewTicket` 参数

```typescript
async function storeToken(params: {
  tokenHash: string;
  purpose: AccessTokenPurpose;
  storeSubdomain?: string;
  orderId?: string;
  publicTicketNo?: string;
  customerEmail: string;
  forceNewTicket?: boolean;  // 新增
}): Promise<string> {
  const days = getExpiryDays(params.purpose);
  await query(
    `INSERT INTO support_access_tokens
      (token_hash, purpose, store_subdomain, order_id, public_ticket_no, customer_email, expires_at, force_new_ticket)
     VALUES ($1, $2, $3, $4, $5, $6, now() + ($7 || ' days')::interval, $8)`,
    [
      params.tokenHash,
      params.purpose,
      params.storeSubdomain || null,
      params.orderId || null,
      params.publicTicketNo || null,
      params.customerEmail,
      String(days),
      params.forceNewTicket ?? false,  // 新增
    ],
  );
  return params.tokenHash;
}
```

### 2.2 `createBootstrapToken` — 透传 `forceNewTicket`

```typescript
export async function createBootstrapToken(params: {
  storeSubdomain: string;
  orderId: string;
  customerEmail: string;
  forceNewTicket?: boolean;  // 新增
}): Promise<string> {
  const token = generateOpaqueToken('bt');
  const th = hashToken(token);
  await storeToken({
    tokenHash: th,
    purpose: 'support_bootstrap',
    storeSubdomain: params.storeSubdomain,
    orderId: params.orderId,
    customerEmail: params.customerEmail,
    forceNewTicket: params.forceNewTicket,  // 新增：透传
  });
  return token;
}
```

## 3. 工单服务层改动 (`src/ticket-service.ts`)

### 3.1 `createTicket` — 去掉 ON CONFLICT

```typescript
// 改动前：
INSERT INTO support_tickets (...) VALUES (...)
ON CONFLICT (store_subdomain, order_id, customer_email) DO UPDATE SET ...

// 改动后：
INSERT INTO support_tickets (...) VALUES (...)
// 直接 INSERT，不再有冲突更新逻辑
```

> `public_ticket_no` 本身仍有 UNIQUE 约束。如果极端情况下 `generatePublicTicketNo()` 产生碰撞（概率极低，`Date.now() % 10000` 仅 4 位），INSERT 会失败。建议在 `createTicket` 中捕获 UNIQUE 冲突错误并重试一次（重新生成 ticket_no）。

### 3.2 新增 `listExistingTickets` — 列出全部未关闭工单

**保留原有 `findExistingTicket` 不变**（仍返回单个工单，用于 `create ticket` 端点的冲突检测）。新增一个函数用于多工单展示：

```typescript
/** 列出同一订单下所有未关闭工单（用于多工单场景展示） */
export async function listExistingTickets(params: {
  storeSubdomain: string;
  orderId: string;
  customerEmail: string;
}) {
  const r = await query(
    `SELECT public_ticket_no, status, issue_type, created_at
     FROM support_tickets
     WHERE store_subdomain = $1 AND order_id = $2 AND customer_email = $3
       AND status != 'closed'
     ORDER BY created_at DESC`,
    [params.storeSubdomain, params.orderId, params.customerEmail],
  );
  return r.rows;
}
```

### 3.3 调用方适配说明

| 调用位置 | 使用函数 | 行为 |
|----------|---------|------|
| `POST /api/support/tickets`（创建工单） | `findExistingTicket` | **不变**：非 `forceNewTicket` 场景仍返回 409 冲突 |
| `GET /api/support/bootstrap`（bootstrap） | `listExistingTickets` | 若 `forceNewTicket=true` → 跳过，直接 `mode:'new_ticket'`；否则若列表非空 → `mode:'existing_ticket'` 并返回工单列表供顾客选择 |

> **关键设计决策**：`create ticket` 端点中的"已有工单则报 409"逻辑**必须保留**。仅当 token 标记了 `force_new_ticket=true` 时才跳过该检测。这样确保：老 bt_ token（forceNewTicket=false）仍然不能重复创建工单；新 bt_ token（forceNewTicket=true）可以创建第 2、3…个工单。

### 4.3 新增 `extractFirstProductImage` 工具函数

```typescript
/**
 * 从订单 items_json 中提取第一件商品的图片 URL。
 * Shoplazza line_items 的 image 字段可能为：
 *   - 完整 URL: https://img.shoplazza.com/xxx.jpg
 *   - 协议相对 URL: //img.shoplazza.com/xxx.jpg
 * 统一补全为 https:// 前缀。
 */
export function extractFirstProductImage(itemsJson: unknown[]): string {
  if (!Array.isArray(itemsJson) || itemsJson.length === 0) return '';
  const first = itemsJson[0] as Record<string, unknown> | undefined;
  if (!first) return '';
  const src = String(first.image || first.product_image || first.image_src || '');
  if (!src) return '';
  if (src.startsWith('//')) return `https:${src}`;
  if (src.startsWith('http')) return src;
  return '';
}
```

### 4.4 新增 `createCustomerComplaintInviteJob` 函数

参照 `createPaidSupportInviteEmailJob` 的结构，关键差异：

| 对比项 | paid_support_invite | customer_complaint_invite |
|--------|---------------------|--------------------------|
| token 类型 | `bt_`（forceNewTicket=false） | `bt_`（**forceNewTicket=true**） |
| event_key | `paid_support_invite:subdomain:order:email` | 不做去重（每次点击都创建新任务） |
| product_image | 不传 | 从 items_json 提取后传入渲染变量 |
| AUTO_SEND | 是 | **否**（只在客服手动触发时立即发送） |
| job_source | `'webhook'` / `'backfill'` | `'manual_invite'` |

```typescript
export interface CustomerComplaintInviteSnapshot {
  storeSubdomain: string;
  storeName?: string | null;
  storeDomain?: string | null;
  orderId: string;
  orderNumber?: string | null;
  orderedAt?: string | Date | null;
  customerEmail: string;
  customerName?: string | null;
  paymentMethod?: string | null;
  cardLast4?: string | null;
  orderAmount?: string | null;
  orderCurrency?: string | null;
  itemsJson?: unknown[];        // 用于提取商品图片
}

export async function createCustomerComplaintInviteJob(
  params: CustomerComplaintInviteSnapshot
): Promise<{ job: any }> {
  const publicBaseUrl = await getEffectivePublicBaseUrl();
  const token = await createBootstrapToken({
    storeSubdomain: params.storeSubdomain,
    orderId: params.orderId,
    customerEmail: params.customerEmail,
    forceNewTicket: true,  // ★ 关键：标记为强制新建工单
  });
  const clientLink = `${publicBaseUrl}/ticket?t=${token}`;

  const productImage = extractFirstProductImage(params.itemsJson || []);

  const rendered = await renderEmailFromTemplate('customer_complaint_invite', {
    store_name: params.storeName || '',
    store_domain: params.storeDomain || buildStoreDomain(params.storeSubdomain),
    order_id: params.orderId,
    order_number: params.orderNumber || params.orderId,
    customer_name: params.customerName || '',
    customer_email: params.customerEmail.trim().toLowerCase(),
    public_ticket_no: '',     // 新工单尚无 ticket_no
    client_link: clientLink,
    paid_at: formatEasternTime(params.orderedAt),
    payment_method: params.paymentMethod || '',
    card_last4: params.cardLast4 || '',
    order_amount: params.orderAmount || '',
    order_currency: params.orderCurrency || '',
    product_image: productImage,  // ★ 新增变量
  });

  const maskedLink = maskClientLink(clientLink);
  const snapshotBody = rendered.html;
  const tokenR = await query(
    `SELECT id FROM support_access_tokens WHERE token_hash = $1`, [hashToken(token)]
  );
  const tokenId = tokenR.rows[0] ? Number(tokenR.rows[0].id) : null;

  const result = await query(
    `INSERT INTO support_email_jobs
      (email_job_no, store_subdomain, store_name, store_domain, mail_domain,
       order_id, order_number, ordered_at, email_type, customer_email, status, scheduled_at,
       token_id, subject_snapshot, body_snapshot, client_link_snapshot, raw_client_link, job_source)
     VALUES ($1,$2,$3,$4,$5,$6,$7,$8,'customer_complaint_invite',$9,'pending',now(),$10,$11,$12,$13,$14,'manual_invite')
     RETURNING *`,
    [
      buildEmailJobNo(),
      params.storeSubdomain,
      params.storeName || null,
      params.storeDomain || buildStoreDomain(params.storeSubdomain),
      getMailDomain() || null,
      params.orderId,
      params.orderNumber || null,
      params.orderedAt || null,
      params.customerEmail.trim().toLowerCase(),
      tokenId,
      rendered.subject,
      snapshotBody,
      maskedLink,
      clientLink,
    ],
  );
  return { job: result.rows[0] };
}
```

### 5.1 新增端点 (`src/admin-routes.ts`)

```typescript
// POST /api/admin/tickets/:publicTicketNo/invite-new-ticket
router.post('/tickets/:publicTicketNo/invite-new-ticket', async (req, res) => {
  try {
    const ticket = await getTicketByPublicNo(req.params.publicTicketNo);
    if (!ticket) {
      res.status(404).json({ ok: false, error: 'Ticket not found' });
      return;
    }

    // 从订单快照中获取完整订单信息
    const snapshot = await getOrderSnapshot({
      storeSubdomain: ticket.store_subdomain,
      orderId: ticket.order_id,
      customerEmail: ticket.customer_email,
    });
    if (!snapshot) {
      res.status(404).json({ ok: false, error: 'Order snapshot not found' });
      return;
    }

    const { job } = await createCustomerComplaintInviteJob({
      storeSubdomain: ticket.store_subdomain,
      storeName: ticket.store_name || snapshot.store_name || '',
      storeDomain: buildStoreDomain(ticket.store_subdomain),
      orderId: ticket.order_id,
      orderNumber: ticket.order_number || snapshot.order_number || '',
      orderedAt: snapshot.paid_at || undefined,
      customerEmail: ticket.customer_email,
      customerName: snapshot.customer_name || '',
      paymentMethod: snapshot.payment_method || '',
      cardLast4: snapshot.card_last4 || '',
      orderAmount: snapshot.order_amount || '',
      orderCurrency: snapshot.order_currency || '',
      itemsJson: snapshot.items_json || [],
    });

    // 立即发送（不等定时器）
    await processDueEmailJobs({ limit: 1, onlyJobId: Number(job.id) });

    await logOperation({
      category: 'ticket',
      action: 'manual_ticket_invite',
      actor: (req as any).agent?.name || 'unknown',
      target: `${req.params.publicTicketNo} → new invite`,
      summary: `客服为订单 ${ticket.order_id} 手动发起新工单邀请`,
      status: 'success',
    });

    res.json({ ok: true, job: { id: job.id, email_job_no: job.email_job_no } });
  } catch (e: any) {
    res.status(500).json({ ok: false, error: e.message });
  }
});
```

### 5.2 Bootstrap 端点适配 (`src/support-routes.ts`)

**A. `GET /api/support/bootstrap` 中处理 `force_new_ticket`：**

```typescript
// payload.purpose === 'support_bootstrap' 分支内
const { store_subdomain, order_id, customer_email } = payload;
if (!store_subdomain || !order_id || !customer_email) {
  res.status(400).json({ ok: false, error: 'Invalid token data' });
  return;
}

const snapshot = await getOrderSnapshot({ ... });
const order = snapshot ? { ... } : null;

// ★ 新增：force_new_ticket 逻辑
if (payload.force_new_ticket) {
  // 手动邀请场景：跳过已有工单检测，始终返回新建模式
  res.json({ ok: true, mode: 'new_ticket', order, ticket: null });
  return;
}

// 原有逻辑：检测已有工单
const existingTicket = await findExistingTicket({
  storeSubdomain: store_subdomain,
  orderId: order_id,
  customerEmail: customer_email,
});

if (existingTicket) {
  // 生成 ta_ token 指向已有工单
  const taToken = await createTicketAccessToken({ ... });
  res.json({
    ok: true,
    mode: 'existing_ticket',
    order,
    ticket: { public_ticket_no: existingTicket.public_ticket_no, status: existingTicket.status },
    accessToken: taToken,
  });
  return;
}

res.json({ ok: true, mode: 'new_ticket', order, ticket: null });
```

**B. `POST /api/support/tickets` 中适配 `forceNewTicket`：**

```typescript
// 原有：始终检测已有工单
const existingTicket = await findExistingTicket({ ... });
if (existingTicket) {
  res.status(409).json({ ok: false, error: 'A dispute already exists for this order', ... });
  return;
}

// ★ 改为：仅当 token 非 force_new_ticket 时才检测
if (!payload.force_new_ticket) {
  const existingTicket = await findExistingTicket({ ... });
  if (existingTicket) {
    res.status(409).json({ ok: false, error: 'A dispute already exists for this order', ... });
    return;
  }
}
// force_new_ticket=true 时跳过检测，允许创建多个工单
```

## 7. 数据流总结

```
客服点击"发起新工单"
  │
  ├─ POST /api/admin/tickets/:no/invite-new-ticket
  │     ├─ 查询工单 → 查询订单快照
  │     ├─ createBootstrapToken({ forceNewTicket: true })
  │     ├─ createCustomerComplaintInviteJob()
  │     │     ├─ extractFirstProductImage(items_json)
  │     │     ├─ renderEmailFromTemplate('customer_complaint_invite', { ..., product_image })
  │     │     └─ INSERT support_email_jobs
  │     └─ processDueEmailJobs({ onlyJobId }) → 立即发送
  │
  └─ 顾客收到邮件 → 点击链接（bt_ token）
        │
        └─ GET /api/support/bootstrap?t=bt_xxx
              ├─ verifyAccessToken → force_new_ticket = true
              ├─ 跳过 findExistingTicket
              └─ 返回 mode: 'new_ticket'
                    │
                    └─ 顾客填写 → POST /api/support/tickets
                          ├─ createTicket() → INSERT（无冲突）
                          ├─ createTicketAccessToken() → ta_ token
                          └─ 返回 ta_ token → 顾客进入工单回复页
```

## 8. 注意事项

1. **`findExistingTicket` 保持不变**：原函数仍返回单个工单（LIMIT 1），用于 `POST /api/support/tickets` 中的冲突检测。新增 `listExistingTickets` 函数用于多工单展示。`create ticket` 端点的 409 冲突逻辑**必须保留**——仅 `force_new_ticket=true` 时跳过。

2. **邮件去重**：`customer_complaint_invite` 类型的邮件不做 `event_key` 去重。每次客服点击都应生成新的邮件任务和新的 bt_ token。

3. **商品图片**：`extractFirstProductImage` 取 `items_json[0]` 的第一张图。如果 Shoplazza 的 `line_items.image` 字段实际名称不同，需要根据真实数据调整（`image` / `product_image` / `image_src`）。建议先用真实订单数据验证字段名。

4. **旧数据兼容**：`ALTER TABLE ... DROP CONSTRAINT IF EXISTS` 和 `ADD COLUMN IF NOT EXISTS` 确保平滑升级。建表语句同步修改以支持全新部署。

5. **`forceNewTicket` 默认值**：`false`，原有流程不受任何影响，完全向后兼容。

6. **`public_ticket_no` 碰撞**：去掉 ON CONFLICT 后，`generatePublicTicketNo()` 的 4 位随机数在高并发下有碰撞可能（概率极低但仍存在）。建议 `createTicket` 中捕获 UNIQUE 冲突异常并重试一次。

7. **`sendEmailJob` fallback 分支**：当 `customer_complaint_invite` 类型 job 的快照丢失时（极端情况），fallback 会调用 `createBootstrapToken` 但**不带 `forceNewTicket: true`**，语义不正确。解决方案：在 `createCustomerComplaintInviteJob` 中确保快照一定被写入；同时在 `sendEmailJob` 中为 `customer_complaint_invite` 增加显式分支。

8. **`invite-new-ticket` 端点建议加限流**：当前仅依赖全局 100 次/分钟的 API 限流（`index.ts` 中 `app.use('/api/', apiLimiter)`）。建议新增独立限流器（如每分钟最多 3 次），防止客服误操作或页面脚本错误导致短时间内重复发送。

9. **`email-templates.html` 预览变量补充**：`livePreview()` 函数中的 `vars` 对象需增加 `product_image: document.getElementById('tv_product_image').value`，否则预览时 `{{product_image}}` 无法渲染。

10. **邮件模板管理页 `switchTemplate` 映射补充**：`defaults` 和 `typeLabels` 对象需新增 `customer_complaint_invite` 条目，否则切到新 Tab 后恢复默认时找不到对应模板。

## 9. Token 链接防滥用分析

### 9.1 当前防护现状

| 防护层 | 现状 | 说明 |
|--------|------|------|
| Token 熵值 | ✅ 已充分 | `bt_` + 32 字节随机数（base64url），256-bit 熵，暴力猜测不可行 |
| 全局 API 限流 | ⚠️ 有但弱 | `index.ts` 中 `app.use('/api/', apiLimiter)` — 100 次/分钟/全局。对单一 IP 反复尝试不同 token 的防护力度有限 |
| Token 单次使用 | ❌ 无 | `verifyAccessToken` 仅设 `used_at`，不阻止重复使用。同一 token 可被无限次访问 |
| 失败锁定 | ❌ 无 | 连续使用无效 token 访问 bootstrap 端点不会被拦截 |
| IP 级别限流 | ❌ 无 | 无针对 token 相关端点的独立限制 |

### 9.2 风险场景

| 场景 | 风险等级 | 说明 |
|------|---------|------|
| 恶意扫描 token | 低 | 256-bit 随机 token 实际不可猜测，但攻击者仍可发送大量无效请求消耗数据库资源 |
| 单个有效 token 被反复访问 | 中 | 顾客的 `bt_` 或 `ta_` token 如果被泄露（邮件转发、浏览器历史等），任何人都可以反复访问工单 |
| 邮件链接被分享 | 中 | 顾客将邮件链接分享给他人，他人可代为查看/回复工单 |
| 旧 bt_ token 重复创建工单 | 低 | 当前 ON CONFLICT 阻止了重复创建；去掉约束后需要靠 `force_new_ticket` 逻辑控制 |

### 9.3 建议增强措施

#### 方案 A：Token 一次性使用（推荐，实现简单）

Bootstrap token（`bt_`）在首次验证后即标记为已使用，第二次访问返回"链接已失效"。这可以防止邮件链接被分享后反复使用。

```typescript
// verifyAccessToken 中：bt_ token 首次验证后标记 revoked
if (row.purpose === 'support_bootstrap' && row.used_at) {
  // 已被使用过 → 拒绝（除非是 force_new_ticket 的 token 且顾客尚未创建工单的场景）
  // 但这样会破坏"顾客点开链接后关闭浏览器再打开"的场景
}
```

> ⚠️ 但这会破坏用户体验：顾客可能点开链接后暂时不填，关闭浏览器后再打开。所以需要更精细的策略：比如 bt_ token 被使用后 24 小时内允许重复访问，超时后失效。

#### 方案 B：Bootstrap 端点独立限流（推荐，低风险）

```typescript
// 在 support-routes.ts 中新增
import rateLimit from 'express-rate-limit';

const bootstrapLimiter = rateLimit({
  windowMs: 60 * 1000,   // 1 分钟窗口
  max: 10,               // 最多 10 次（正常顾客最多 2-3 次）
  standardHeaders: true,
  legacyHeaders: false,
  message: { ok: false, error: '访问过于频繁，请稍后重试' },
});

// GET /api/support/bootstrap 路由应用此限流
router.get('/bootstrap', bootstrapLimiter, async (req, res) => { ... });
```

#### 方案 C：失败令牌计数 + 临时封禁（中等复杂度）

连续 N 次提交无效 token 后，对该 IP 临时拒绝服务（如 5 分钟内返回 429）。实现方式可复用现有 `rateLimit` 的 `skip` 回调——成功验证时跳过计数。

#### 方案 D：Token 绑定 email（当前已隐含实现）

当前 `verifyAccessToken` 查询数据库已验证的 token hash，未在数据库中找不到的 token 直接返回 null。这已经是最基础的保护——只有真实发送过邮件的 token 才能通过验证。但由于没有失败计数，攻击者仍可高频尝试。

### 9.4 针对本功能的推荐实施方案

| 措施 | 优先级 | 成本 | 说明 |
|------|--------|------|------|
| Bootstrap 端点独立限流（方案 B） | **高** | 3 行代码 | 对 `GET /api/support/bootstrap` 加 10次/分钟 限制，有效阻止恶意扫描 |
| `invite-new-ticket` 端点独立限流 | **高** | 3 行代码 | 对 `POST /api/admin/tickets/:no/invite-new-ticket` 加 3次/分钟 限制，防止客服误操作 |
| Token 首次使用后设冷却期 | 中 | ~20 行 | `bt_` token 首次验证后 24h 内允许重复，超时失效；`ta_` token 不做此限制 |
| 失败令牌 IP 临时封禁 | 低 | ~40 行 | 当前 256-bit token 已足够安全，投入产出比不高 |

### 9.5 结论

Token 本身的 256-bit 随机性已提供了足够强的防猜测保护。当前最实际的威胁不是 token 被暴力破解，而是：
1. **单个有效 token 被泄露**后反复使用（邮件转发等）
2. **恶意 IP 高频请求**消耗数据库资源

建议至少实施方案 B（bootstrap 独立限流），方案 D（token 冷却期）可按需后续迭代。
