# Webhook 接收及物流核验调整

用户已要求直接实现，沿用 main、作者 ANOKO1122、推送及部署，不创建 PR、不备份。

## 范围与选择

- 取消 webhook 每店 600/min 限额；保留鉴权、普通管理 API 限流、512KB 请求限制、持久化后应答、幂等及 worker 重试。
- 原方案全店共享 200 单且逐单 GET。改为每店每轮最多 1,000 单，按 50 个订单 ID 一组 GET 订单列表并读取完整 fulfillments；验证分页、返回 ID 和数组结构，缺失订单不能当空物流成功。
- 定时仍每小时运行。普通已支付/部分退款订单只核验上游下单时间最近 30 天的订单，成功后 24 小时复查；最近 30 天有顾客/客服工单活动的关联订单优先，允许例外检查老订单，成功后 6 小时复查。用户已确认老订单例外。
- 工单活跃使用创建、顾客消息、客服消息、关闭及 updated_at 操作时间；代码已确认 updated_at 由人工回复、重开、仲裁、状态操作维护，顾客浏览与订单同步不修改它。过期工单取消重点资格，老订单退出自动核验。手动明确指定订单可跳过自动日期和到期限制。
- 各店优先队列和普通队列各自按最早应查时间轮转，优先队列先取；任一店不得消耗其他店的额度。失败 1 小时后重试，不推进成功时间。
- 继续通过既有包裹合并器保留旧号码，只更新物流，不发邮件，不触发历史订单恢复和付款通知。
- 成功 webhook 保留现有原始事件、接收/处理时间、重投次数和处理错误。拒绝原因增加安全的持久化操作日志（无密钥、URL query、邮件和正文）。物流汇总增加按店额度、批量请求数量和重点单计数，方便两天后对账。

## Approaches

1. 仅提高全局 200 上限：仍逐单调用，且老订单和大店挤占额度，不采用。
2. 按店额度、近期订单及活跃工单筛选、按 ID 批量查询：按用户方向采用。
3. 只靠 webhook：保留为主路径，但不撤销补漏核验。

## 边界与验证

- 不使用本地 snapshot.created_at 充当下单时间；优先 raw_order_json.placed_at，再用上游 created_at，缺失时用已有 paid_at；不把本地新建的老订单重新纳入 30 天。
- 批量 API 必须实测 ids 参数及完整物流；错误、游标循环、无关订单、缺失 fulfillments 不能记成功；唯一已实测的合法例外是返回订单 fulfillment_status=waiting 且省略 fulfillments 字段，此时按空数组处理，显式 null 及其他状态仍失败。
- 选择 SQL 在隔离测试数据库验证多店、重复快照、工单有效期、订单年龄和到期公平性；生产只读 EXPLAIN/候选统计。
- 保留用户已有 admin-stores.html 修改及 support-system/tmp，不纳入提交或部署。
- 本次不自动补跑已发现的 50 个缺失历史订单，不创建延后发送通知。
